03 · 方向演化史

不是"选了 x402"，是排除法排到了 x402

三次方向否定，一次定稿。每次否决的理由，比最终方案更值得记住——它们构成了永久非目标清单。

✗否决 ①

公共物品类合约（提案 / 治理 / 募资）

受众小、非刚需——演示热闹，赛后无人复用。

✗否决 ②

Agent 任务市场（雇主发任务 → Agent 做 → 验证放款）

看起来最像"Agent 经济"，实际撞上三个死锁：

死锁一｜有验证测试包的雇主，自己用 coding agent 就写完了，不需要市场 死锁二｜非确定性验证（LLM-Judge / 人工）= 纠纷机器 死锁三｜微额佣金养不活平台运营
✓定稿

x402 式按次付费服务调用

支付是确定性事件（验签即确定），不需要验证交付物——同步 HTTP 请求-响应、当场验货 + 复购纪律，三个死锁被结构性绕开，而不是被解决。

推论本项目全部设计均以"交付验证问题不存在"为前提——凡是重新引入验证 / 裁决 / 验收的提案，都是回潮。

05 · 热路径

一次付费调用：七步，全部确定性判断

计费不依赖任何人工审批、LLM 裁决或交付物验收；签名即支付承诺，链上动作被推迟到异步结算。

1
认证 网关
api key → 消费者记录；无 key → 402（附注册指引）
2
查服务 目录缓存
读 manifest；status ≠ active → 404
3
Schema 校验
请求体不符 input_schema → 422，不产生任何计费
4
幂等 X-Idempotency-Key
同 key 同 body → 返回上次结果，不重复计费；同 key 异 body → 409
5
支付验证 + 影子闸门 核心
本地验签：ecrecover == 消费者钱包 · deadline 窗口 · 金额 == 定价 · nonce 未重放；链上约束（eth_call 短缓存）：approve ≥ 余额 ≥ 定价；影子闸门（内存、fail-closed）：在途笔数 < K=3——任一不过 → 402 质询（x402 同构 JSON）
6
代理转发 Provider postpay
2xx → 结果透传，签名授权入 settle 队列；失败 / 超时 → 从未扣款，零退款逻辑
7
收据返回 网关
X-Receipt-Id / X-Charged-Raw 随 200 下发（HMAC 防伪，result_hash 存证）
异常全表余额 / 授权不足 → 402（损失 0）；签名无效 / 重放 → 401/409（0）；Provider 挂 → 不入队不扣款（供应方一次计算成本）；撤 approve 竞态 → 影子闸门限幅，损失 ≤ K×单价；keeper 宕机 → 队列续批（0）。
06 · 核心裁决

六轮挑战收敛出的四条不可让步项

每一条都是发起人面对"如果出 bug / 官方上线 / 有人作恶怎么办"给出的回答——设计目标是最坏情况可控，而不是平均情况漂亮。

裁决一 · 铁律 P7/P8

资金永不过平台手

动机直说：怕 bug 资损。平台只提供合约，不设平台收款账户；消费端钱包经链上合约 直接扣款给 Provider。提现路径无 pause、无 admin 锁——合约任何 bug 最坏后果 = 服务停摆，而非资金冻结。

挑战：平台垫资结算不是更快吗？——快不等于敢；托管一分钱，审计责任多一吨。
裁决二 · 时序

postpay：转发成功才扣款

调用 → 转发成功 → 才扣款。失败 = 从未扣款，退款代码为零。x402 原生是 prepay + 退款——这是语义差异，不是成熟度差异；postpay 把"退款纠纷"这个类别整个删掉了。

挑战：不怕被白嫖吗？——怕，所以有裁决三。
裁决三 · 限幅

影子在途闸门，K = 3

验签后不立即上链（同步调用等不起出块）：网关内存里限每 key 在途 K=3 笔并发。最坏情况（撤 approve 竞态 + keeper 失败）下，白白调用的损失封顶 K×单价。性能层而非资金层，fail-closed。

挑战：K 会不会太小？——它是损失上限不是吞吐上限；坏账笔拉黑 key 兜底。
裁决四 · 合约

PayVault：手搓 EIP-3009 语义

Base 上 USDC 原生自带 transferWithAuthorization，BOT 链代币没有——所以我们自部署 PayVault 把同语义补出来：EIP-712 授权 + ecrecover + nonce 防重放 + keeper 批量执行。协议形状与 x402 对齐（铁律 P9）。

挑战：官方上线后合约白写？——见下页 L0~L3 与角色演化。
07 · 结算层

PayVault 记账，keeper 批量上链

网关只验不上链；结算异步发生：keeper 攒批 → 一笔 chargeWithSigBatch → Charged 事件上屏。链上余额即对账，v1 的对账端点被链本身替代。

合约 PayVault 零依赖单文件 · 目标 ≤160 行

  • chargeWithSigBatch(calls[])：仅 keeper 可调；逐笔验 deadline → nonce 未用 → ecrecover==from → transferFrom 进合约 → 按 Provider 记账；单笔失败跳过 + ChargeFailed 事件，不毒死整批
  • providerWithdraw：按记账额度提现到 agentWallet，任何人可触发，无 pause、无 admin 锁（P8）
  • 安全不变量写进测试：I1 operator 无提钱路径 · I2 同 nonce 永不双扣 · I3 消费者 approve 主权不受合约干预 · I4 合约余额 == Σ未提现记账（链上即对账）
x402 对照：USDC 内置 transferWithAuthorization ↔ chargeWithSig；facilitator 代提交 ↔ keeper 批量；facilitator 赞助 gas ↔ keeper 账户付 gas。

08 · 官方上线之后

payment_scheme 平台级抽象：迁移 = 换适配器

接口签名以 Base USDC x402 的形态为设计标尺，所有 x402 语义收口在 payment_scheme 模块（铁律 P9）；SDK 签名格式与 x402 对齐，消费者代码零改动。

级别触发条件（官方 eventual 形态）动作成本
L0 仍不可用 / 仅文档（现状） 零动作——PayVault 承重；演示话术含"官方仍占位" 0
L1 官方支付合约 / facilitator 上线 payment_scheme 增加 "eip3009-native" 适配器：验签对象与结算目标切官方合约，网关 / SDK 骨架不动 约半天
L2 官方引入带 3009 的代币 SDK 加对应 scheme 的 EIP-712 签名器（eth_account sign_typed_data 现成），双 scheme 灰度——全官方 约 1 天
L3 Base 适配（V1.5 / V2，可选） 同一 ChainAdapter 接口插入 Base adapter；Base 上 USDC 原生 3009，keeper 直接提交授权——零自建合约 见 08 任务卡
PayVault 的角色演化短期是承重墙（官方没上线，没有它平台收不了一笔钱）；长期是自托管 postpay 轨道 + 谈判筹码——官方上线作废的只是"唯一性"头衔，不是合约本身的价值。
09 · 诚实边界

哪些不做、为什么，赛前先说清楚

边界不是减配，是把三个死锁挡在系统外；剩下的风险如实相告，不修饰。

铁律 P6 永久非目标

  • 任务撮合 / escrow 裁决 / 事后验收——重新引入交付物验证 = 死锁二回潮（纠纷机器）
  • LLM-Judge / 多 Agent 交叉评价——非确定性验证不可收单；信誉只认链上收入这一硬指标
  • 平台佣金——微额抽佣养不活争议运营（死锁三）；我们收全额转嫁、做协议与收单基础设施
  • 让有验证器的雇主来发任务——他们自己就有 coding agent（死锁一）

如实相告 剩下的风险与缓解

  • 合约未经审计——缓解：消费者 approve 限额自主可控（损失敞口=approve 上限）+ P8 提现永开 + 演示小额；写进演讲结尾
  • 链上实测活跃度有限（我们尽调数据）——平台当前价值 = 赛时真实闭环 + Agent 经济的协议位（x402 时代）+ 全链上可验证结算
  • 不做 GMV 修饰——overview 大屏的数字就是全部真实发生过的调用，每个都可拿交易哈希去 scan.bohr.life 核验
  • 官方时间表未知——我们只陈述实测（占位 / 内网不可达），不预测官方上线时间
